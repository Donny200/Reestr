# Публичный каталог: инструкции, контакты, подбор, сообщения, проверка и сохранение

Публичный сайт остаётся информационным каталогом. Посетитель читает опубликованные карточки без входа в систему.
Онлайн-заявки, платежи, запись на приём и учётные записи граждан не добавлялись.

## Что найдено в проекте и какие решения приняты

- Карточка услуги — `OrgFunction` в `function_catalog_db`, организация — `Organization` в `adlita_project1`,
  регионы — `regions` в `reference_service_db` (только `name` и `code`).
  Организация хранит необязательный `region_code` как мягкую ссылку без внешнего ключа между базами.
  Название региона фронтенд получает из `GET /api/regions`.
- Переводы карточек используют существующий формат `{код языка: {text, source}}`, где `source` равен `human` или `machine`.
  Шесть новых полей инструкции хранят переводы в одном JSONB `instruction_translations` в виде `{поле: {язык: {text, source}}}`.
  Изменение исходного поля удаляет машинные переводы этого поля и сохраняет ручные, как это уже было для названия и описания.
  Очистка исходного поля удаляет все переводы этого поля. Ручное сохранение перевода помечает его `human`.
- Прежнее поле `requirements` сохранено без изменений. Если структурированный список документов пуст,
  публичная страница показывает требования под заголовком «Требования». Если список заполнен, требования выводятся как «Дополнительные требования».
- Данные не выдумывались. Миграции добавляют пустые колонки, сиды не менялись.
  Пустое поле на публичной странице помечается как «Пока не указано» или «Не указано».
- Права: `REPORTS_VIEW` уже был в каталоге прав, назначался ORG_ADMIN и MODERATOR и нигде не использовался.
  Он переиспользован для чтения сообщений. Для смены статуса добавлен один новый код `REPORTS_MANAGE` (категория `Reports`).
  Отметку проверки карточки выполняет существующий `FUNCTIONS_REVIEW`, отметку проверки организации —
  `ORGANIZATIONS_EDIT` или `ORGANIZATIONS_EDIT_OWN` для своей организации.
- SUPER_ADMIN получает `REPORTS_MANAGE` прежним механизмом. ORG_ADMIN получает его только при первичной инициализации роли.
  Существующие назначения ролей автоматически не расширялись; при необходимости право назначается на странице ролей.
- Сообщения хранятся в `function_catalog_db`: там уже есть `audit_logs`, а JWT содержит `organizationIds` для ограничения по организации.
  В шлюз добавлен маршрут `/api/reports/**` к function-catalog-service.
- Внутреннего сервиса уведомлений в проекте нет, поэтому письма не отправляются.
  Вместо этого добавлены карточки на панели управления и фильтры «Нужна проверка».
- Платные картографические API и новые ключи не используются. При наличии координат публичная страница даёт ссылку на OpenStreetMap,
  администратор может указать собственную ссылку на карту. Встроенных карт нет, поэтому браузер посетителя не обращается к сторонним сервисам без клика.

## API и права

| Метод и путь | Доступ |
|---|---|
| `POST /api/reports` | Анонимно, с ограничением частоты |
| `GET /api/reports?status=OPEN\|ALL\|NEW\|IN_PROGRESS\|RESOLVED\|REJECTED&entityType=&entityId=` | `REPORTS_VIEW` или `ORG_REPORTS_MANAGE` и организация пользователя |
| `GET /api/reports/{id}` | `REPORTS_VIEW` или `ORG_REPORTS_MANAGE` и организация пользователя |
| `PUT /api/reports/{id}/status` | `ORG_REPORTS_MANAGE` или `REPORTS_VIEW` + `REPORTS_MANAGE` и организация пользователя |

Статусы `IN_REVIEW` и `DISMISSED` заменены на `IN_PROGRESS` и `REJECTED`, полный процесс описан в
[organization-analytics.md](organization-analytics.md).
| `POST /api/functions/{id}/verify` | `FUNCTIONS_REVIEW` и организация пользователя; нужна ссылка на официальный источник |
| `POST /api/organizations/{id}/verify` | `ORGANIZATIONS_EDIT` или `ORGANIZATIONS_EDIT_OWN` для своей организации; нужна ссылка на официальный источник |

Изменения существующих контрактов обратно совместимы:

- `POST/PUT /api/functions` принимают `instructions` (`whoCanUse`, `steps`, `requiredDocuments`, `whereHowToApply`, `processingTime`, `fee`)
  и `officialSourceUrl`. Переданный объект `instructions` полностью заменяет шесть полей, пустое значение очищает поле.
  `officialSourceUrl`: `null` — без изменений, пустая строка — очистить.
- `PUT /api/functions/{id}/translations/{language}` дополнительно принимает карту `instructions`.
  Перевод поля без исходного текста отклоняется с 400.
- `POST/PUT /api/organizations` принимают `contact` (`address`, `phone`, `workingHours`, `latitude`, `longitude`, `mapUrl`, `regionCode`)
  с полной заменой блока и `officialSourceUrl`. Широта и долгота задаются только вместе.
- Ответы карточек и организаций содержат `lastVerifiedAt` и `verificationStatus`.
  `verifiedByUserId` возвращается только в административных ответах.

## Проверка по официальному источнику

| Статус | Значение |
|---|---|
| `UNVERIFIED` | Проверка не выполнялась |
| `VERIFIED` | Проверено менее 180 дней назад, ключевые поля не менялись |
| `DUE` | Последняя проверка старше 180 дней |
| `OUTDATED` | Ключевые поля изменились после проверки |

Ключевые поля карточки: название, описание, организация, требования, шесть полей инструкции и ссылка на источник.
Ключевые поля организации: название, контактный блок и ссылка на источник.
Категория, переводы и описание организации проверку не сбрасывают.
Публичная страница при `OUTDATED` прямо сообщает, что новая проверка ещё не выполнена, и не называет данные проверенными.
Отметка проверки записывается в `audit_logs` (`VERIFY`) для карточек и в журнал приложения для организаций, где отдельного аудита нет.

## Сообщения посетителей: защита и приватность

- Строгая проверка: тип объекта, положительный id, категория из списка и применимая к типу объекта,
  описание 10–2000 символов после нормализации и не более трёх ссылок, контакт — пустой, e-mail или телефон, язык — языковой тег.
- Сообщение принимается только для опубликованной карточки или активной организации. Черновики дают 404.
- Скрытое поле `website` служит ловушкой для ботов: такие запросы получают 202 и не сохраняются.
- Ограничения частоты настраиваются в `catalog.reports.*`: 5 сообщений за 15 минут на клиента,
  200 в час на весь сервис и 30 в сутки на один объект. Повтор того же текста по тому же объекту за сутки не создаёт дубль.
  Превышение возвращает 429 с `Retry-After`.
- Клиент определяется по заголовку `X-Real-IP`, который Nginx перезаписывает реальным адресом.
  В памяти хранится только SHA-256 от адреса с солью, создаваемой при запуске. IP-адреса в базу не пишутся.
  Шлюз Spring Cloud Gateway 4.3 без `trusted-proxies` не добавляет X-Forwarded-заголовки и пропускает `X-Real-IP` без изменений.
  Порт шлюза 8082 не следует публиковать в production, иначе клиент сможет подменить заголовок; общие и объектные лимиты продолжат действовать.
- Контакт видят только сотрудники, которые обрабатывают сообщения своей организации (`ORG_REPORTS_MANAGE` или `REPORTS_VIEW` + `REPORTS_MANAGE`).
  Сотрудник только с `REPORTS_VIEW` видит лишь отметку, что контакт оставлен. Контакт удаляется при статусе `RESOLVED` или `REJECTED`.
- Аудит: `REPORT_RECEIVED` с исполнителем `public:anonymous` без текста и контакта, `REPORT_STATUS_CHANGE` с автором из JWT.
- Сообщения никогда не меняют карточку или организацию. Исправление идёт обычным редакционным процессом.

## Подбор, сохранение, печать и отправка ссылки

- `/finder`: три шага — жизненная ситуация (категории с опубликованными услугами), цель (необязательные ключевые слова)
  и организация (только организации с подходящими услугами). Поиск выполняется в браузере по публичным данным,
  введённый текст никуда не отправляется. Пустой результат предлагает очистить ключевые слова, выбрать другую ситуацию или открыть весь каталог.
- `/saved`: список хранится только в `localStorage` под ключом `reestr-saved-services` (до 100 услуг) и синхронизируется между вкладками.
  Список не отправляется на сервер. Есть удаление по одной услуге и очистка всего списка.
- Печать использует `@media print`: шапка, подвал и кнопки скрыты, тёмная тема заменяется светлой,
  добавляется заголовок с датой и адресом страницы, документы печатаются как чек-лист.
- «Поделиться» вызывает `navigator.share`, иначе копирует ссылку в буфер обмена, иначе показывает ссылку для ручного копирования.

## Миграции

| Сервис | Файл | Содержание |
|---|---|---|
| function-catalog-service | `V3__service_instructions_verification_reports.sql` | Колонки инструкции, источника и проверки в `org_functions`, таблица `information_reports` с индексами |
| identity-service | `V3__organization_contact_and_verification.sql` | Контактные колонки, источник и проверка в `organizations`; выполняется только если таблица уже есть |
| reference-service | `V4__public_catalog_enhancement_labels.sql` | 188 подписей интерфейса на en, ru, uz и fr |

Все миграции только добавляют данные (`ADD COLUMN IF NOT EXISTS`, `CREATE TABLE IF NOT EXISTS`, `ON CONFLICT DO NOTHING`).
Существующие строки не изменяются и не удаляются.

## Данные, которые должны заполнить администраторы

После миграции новые поля пусты у всех существующих записей. Значения нужно взять из официальных источников и внести через административную консоль.

Для каждой карточки услуги (`/admin/functions/{id}`):

- кто может воспользоваться услугой;
- порядок действий;
- необходимые документы;
- где и как обратиться;
- срок оказания;
- официальная плата;
- ссылка на официальный источник, после чего карточку отмечает проверенной рецензент.

В коде известны такие записи: три демонстрационные опубликованные карточки «Passport renewal», «Marriage registration»,
«Business license application» (организация 1; в требованиях упоминается плата без суммы, сумма не выводилась)
и восемь редакционных черновиков из `seed/editorial-functions.json`.

Для каждой организации (`/admin/organizations`, «Изменить»):

- официальный адрес и регион;
- телефон;
- часы работы;
- координаты или ссылка на карту, если они нужны;
- ссылка на официальный источник, после чего организация отмечается проверенной.

`AdminFunctionsBrowserIT` падал и на неизменённом коде: после редизайна вкладки языков получили скрытую подпись
«Some translations are missing.», а `backend-flow.spec.ts` искал вкладку по точному имени. Локатор заменён на поиск по началу имени.

Миграции дополнительно применены к отдельному временному контейнеру PostgreSQL 16: reference V1–V4 выполнились без ошибок,
identity V3 ничего не делает на пустой базе, добавляет колонки к существующей таблице без потери строк и безопасно повторяется.
Проектная база, тома Docker и рабочие контейнеры не использовались.

## Развёртывание

Пересоберите identity-service, reference-service, function-catalog-service, api-gateway и front.
Сотрудникам нужно обновить сессию, чтобы JWT получил новые права. Тома и базы данных не пересоздаются.
